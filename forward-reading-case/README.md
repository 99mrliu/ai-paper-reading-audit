# 表里79小时、正文79.2小时：怎样核查AI给出的解释？

Strubell等ACL2019论文Table3的BERT行写79小时、1507kWh、1438lb；正文另写79.2小时。AI能找到原文，却仍可能把“79.2可以解释”写成“只有79.2，且证明作者内部这样算”。本实践解决这个具体阅读问题：把精确复算、显示舍入、共同参数和内部过程证据分开。

原论文为Emma Strubell、Ananya Ganesh、Andrew McCallum，Energy and Policy Considerations for Deep Learning in NLP，ACL2019，pp.3645–3650，P19-1355。[完整6页原PDF](INPUT/paper.pdf)、页图、实际提问、AI输出与代码均随包；出处和CC BY4.0说明见[SOURCES.md](SOURCES.md)。不需要联网下载才能核查。

## 真实实践：找到出处之后仍会出错

第一段是在玻尔科学空间0.10.11进行的真实两轮阅读。[操作教程与作者复核](science-space/REVIEW.md)包含本地导入、首次任务启动未完成后的入口调整、原PDF提取、两次实际提问及局限。[完整可见答复](science-space/conversation-ax.txt)保留首答“只有79.2小时才成立”，以及追问后撤回唯一性的修订；原答未覆盖。后续答复还算错了另一个201kWh换碳问题，作者已明确指出，不能因追问完成就视为全部通过。

这促成两个必要改进：候选解释不能覆盖名义失败；“只有”必须接受邻近反例或区间检查。冻结的[paper-budget-audit v1.1.1](skill/SKILL.md)把它们写成可操作规则。

第二段是在干净输入目录执行的新Codex会话：只给同一原PDF、[实际任务](INPUT/task.md)、[实际提示](prompt.txt)和该Skill，不给旧答案。它实际输出：

> 因此79.2不是唯一解，反例也不证明作者用过79.21。若79是整数显示舍入值，也不能排除此区间。

[完整原报告](out/report.md)、全部11条名义/候选记录、[声明](out/claims.json)、[会话环境](session.json)与关键操作均保留。该任务还审查同值同源及外部电表两条引用，完整材料没有删掉不便展示的部分；本文主线只展开BERT时长。用时142.271秒，9次工具调用，准确模型快照与账单未知。

## 三个判断，需要三种检查

固定PUE、功率和因子，E(t)=19.0255858t kWh，C(t)=18.1504088532t lb。这些是按论文公式得到的合计率，不能再乘64。

| 检查 | 实际结果 | 允许的结论 |
| --- | --- | --- |
| 将79当精确输入 | 1503.0212782kWh、1433.8822994028lb | 与印刷1507/1438的精确值及整数舍入均不符；失败保留 |
| 将正文79.2代入 | 1506.82639536kWh、1437.51238117344lb | 在整数四舍五入假设下兼容，不是精确相等 |
| 将构造79.21代入 | 1507.016651218kWh、1437.693885261972lb | 同样兼容，否定“只有79.2”；不能说作者用过79.21 |

当79本身也是整数舍入显示时，它约束的是一个区间，而不是精确点。不能一方面允许1507/1438取整，另一方面默默把79当无误差的精确观测。

另一个容易漏掉的问题是共同参数：分别存在某个时长使能量兼容、某个时长使排放兼容，不证明同一个时长能同时满足。我们用既有计算器实际构造了[两个独立标志都为true却无共同解的反例](joint-check/legacy-output.json)。它是合成边界例，不是论文观测，旧工具也从未承诺联合可行。

新增[paper-joint-rounding Skill](joint-check/skill/SKILL.md)将每项约束反解到同一非负时长轴，以Fraction精确有理数求交，并保留端点开闭。它只支持固定正系数的线性模型和明示取整规则，不处理未知单位、多参数相关误差或物理验证。

在half_up和输出整数显示假设下：能量允许约[79.182844399,79.235405198)，排放允许约[79.199317857,79.254413035)；时长79按步长1显示允许[78.5,79.5)。三者交集为约[79.199317857,79.235405198)。所以精确79不通过，但显示79、1507、1438可以在同一条件模型下联合成立。

端点不是实现细节：构造的t显示2、3t显示8，步长都为1，half_up交集为空，half_even却仅允许t=2.5。不能用保守闭区间在边界相接就宣布严格可行，更不能由某规则下兼容推断作者实际采用它。[技术推导、原输入、开发结果及适用范围](joint-check/README.md)完整保留。

## 新工具是否被正确使用：又一次实际阅读

第三段新会话只给原PDF、联合约束Skill和[任务](joint-check/reading/INPUT/task.md)，没有给教程、旧答案或预期判定。[实际报告](joint-check/reading/out/report.md)写道：

> 分别的见证不能合成同一个t。

它实际运行了11次脚本调用，区分构造例的独立/联合判定、BERT三个候选和两种端点规则；[全部调用日志](joint-check/reading/out/execution-log.json)及每份原始*.input.json和*.result.json原样保留。作者侧重算全部11次，逐项相同。用时138.889秒，10次工具调用，准确默认模型未知。完整原生轨迹附件属于这一会话，较早会话用包内真实输入输出和完整关键操作选录取证，未混称。

## 读者怎样复做，怎样判断完成

只复算已有产物：

```sh
python3 recheck.py
```

仅用标准库，在临时目录重算原9份JSON、22项输入边界测试、新12项联合约束开发测试、11次新阅读调用；不联网、不调用模型、不改保存的原输出。构造例联合不兼容、79精确候选失败都是应保留的正确结果，不能为了“全绿”删除。退出0不证明原文解释或科学测量正确。

重新执行AI阅读：新建空目录，将原PDF放入INPUT/paper.pdf；选择实际任务与对应Skill复制进去，准备out目录，再提交对应prompt.txt。原有阅读使用根目录INPUT/task.md和skill；联合核查使用joint-check/reading/INPUT/task.md和joint-check/skill。不要复制旧out答案。模型需自己的服务账号；提取PDF另需Poppler，生成页图需PyMuPDF。CLI使用0.164.0-alpha.11.1，详见session.json与实际提示，不能保证服务端快照可重建。

验收应回到同一原文检查：是否冻结79精确复算失败？是否区分候选兼容与唯一性？是否让多项约束共享同一时长？是否明示取整规则及范围？是否仍拒绝由兼容证明作者内部计算？科学空间的可点击操作步骤和两轮实际提示见science-space/REVIEW.md。

## 核查到哪里停止

原作者未取整输入、取整实现、跨硬件功率来源和底层采样日志仍缺失。本作品只有条件可行性及原文支持程度，不能验证实际测量，也不把区间当置信区间。

旧报告和新报告均自述视觉核查，但导出轨迹直接证明的是提取/渲染操作，未提供独立图像查看遥测；不能把生成PNG说成证明每次查看。页图及完整PDF供读者再核对。

规则来自已知问题，任务也针对该难点，不是盲测。12项开发测试证明工具在列出的输入上执行正确，新会话证明一次实际使用完成，二者不能合并成AI准确率、速度、费用或稳定收益。平台间没有公平对照，不比较优劣。论文原文、AI实际输出与作者侧判断分开保存；本次贡献与授权见SOURCES.md。
